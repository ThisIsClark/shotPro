# 投篮反馈与复测：第一、第二阶段设计

日期：2026-11-02\
状态：本地试点已实施；实际存储、路由与首版边界见 [实现说明](feedback-pilot-implementation.md)\
范围：第一阶段“交付反馈”；第二阶段“完成复测”。

## 1. 产品决策

**最终交付必须包含建议，不是只给数据。** 用户应当获得：一个优先训练重点、可查看的视频证据、一个具体练习、清楚的复测方式。关键帧和角度是支持判断的材料。

本版采用“算法辅助 + 人工确认”的服务流程：算法提取关键帧和候选观察，反馈者核实后填写建议，用户练习并复测。算法结果不得直接冒充经过教练确认的诊断。管理员身份不等于专业教练身份，页面如实显示反馈者姓名及身份。

这是验证用户价值的试点方案，不是已验证的商业模式。它引入人工服务成本；需要记录每份反馈的耗时，再判断是否能收费、是否值得自动化。若无人能对技术建议负责，不能把自动分析包装为人工专业反馈。

### 目标用户与完成标准

- 用户：有明确投篮困扰、愿意练习和复拍的业余玩家。
- 第一阶段完成：用户能收到包含证据与可执行建议的反馈。
- 第二阶段完成：同一用户能完成练习、关联上传复测、收到下一轮反馈。
- 不承诺单次分析能提升命中率，也不把短期数据变化直接归因于产品。

### 首版不做

教练市场、教练自助入驻、聊天、语音标注、大型训练库、自动训练计划、自动提升百分比、新支付体系、新一轮姿势评分算法。沿用英文界面，新增文案按现有国际化方式组织。

## 2. 当前代码与复用边界

| 现有模块 | 可复用能力 | 本版调整 |
|---|---|---|
| `app/services/analysis_service.py` | 姿态、关键帧、角度、分析输出 | 保持原始输出；人工修正独立保存 |
| `app/api/routes/upload.py` | 上传、后台分析、结果与历史 | 新流程关联主题、持久化原视频、独立处理复测权益 |
| `app/api/deps.py` | 必须登录、管理员鉴权 | 复用；补充主题归属校验 |
| `app/services/db_service.py` | Supabase 持久化 | 增加主题、反馈、练习与媒体记录 |
| `app/services/storage_service.py` | 对象存储封装 | 新流程使用私有媒体，不返回永久公开地址 |
| `templates/index.html` | 上传、结果、历史、关键帧与曲线 | 加入新流程入口；新编辑页独立拆分 |
| `app/api/routes/export.py` | 图片、PDF 导出 | 保留；不是本版网页分享的实现 |

实施前已确认的基础问题：

1. `upload.py` 在分析成功和失败后都会删除本地原视频。新流程必须先可靠保存媒体，算法失败也要允许人工查看。
2. `main.py` 启动清理及上传侧旧任务清理使用数量限制。训练主题关联的素材不得被旧清理逻辑删除。
3. `/results` 是静态挂载目录；Storage 服务当前提供公开 URL。新私有媒体不能放在这些可公开访问的位置。
4. 本地管理员和 Supabase 用户并存。反馈作者使用带来源的身份标识，不能假定管理员 ID 是 Supabase 用户 UUID。
5. 已有 `docs/v2-plan.md` 是曲线与模板比较方案。本文件另行描述反馈和复测，不覆盖旧文档。

## 3. 角色与权限

| 角色 | 权限 |
|---|---|
| 登录球员 | 创建自己的主题、上传、查看已发布反馈、填写练习记录、复测、控制分享、删除主题 |
| 管理员反馈者 | 查看试点队列、查看素材、修正关键帧、编辑草稿、发布反馈 |
| 持有分享链接的人 | 只读指定已发布反馈及其授权媒体；不能编辑、查看草稿或浏览用户其他记录 |

首版不引入独立教练角色。所有业务接口都由后端验证身份和资源归属，不能只靠前端隐藏按钮。数据库使用服务角色时仍须执行这些校验。

## 4. 第一阶段：交付反馈

### 4.1 用户流程

1. 获得试点资格的登录用户进入“Get feedback”。
2. 选择目标并描述困难，选择视频场景，上传一个清晰的投篮片段。
3. 上传成功立即建立持久记录；媒体处理和自动分析分别显示状态。
4. 自动结果可查看，明确标为自动观察；人工反馈显示“Awaiting review”。不承诺未经确认的交付时限。
5. 管理员完成反馈并发布。
6. 用户查看训练卡和对应视频证据。第一阶段尚未开放复测时不显示不可用的提交按钮；第二阶段启用后显示复测入口。

首版建议一个片段展示一次完整投篮；多次投篮的视频由反馈者明确标注本次关注的片段，不暗示算法已分析全部投篮。

### 4.2 上传表单

| 字段 | 规则 |
|---|---|
| 目标 `goal` | 必填：quicker_release / range / consistency / other |
| 困扰 `problem_description` | 必填，1–1000 字符；other 同样要求明确描述 |
| 场景 `shot_context` | 必填：stationary / catch_and_shoot / off_dribble / other |
| 视频 | 沿用现有类型和大小限制；服务端实际校验 |
| 投篮手等配置 | 沿用现有字段 |

上传前说明：视频用于本次反馈与复测，分享由用户主动开启。普通自动分析入口继续存在，不自动承诺人工服务。

### 4.3 管理员队列和编辑页

队列显示主题、用户目标、上传时间、媒体/算法状态、反馈状态，可筛选待处理、草稿、已发布。首版不做人员分配。

桌面布局：

```text
┌─────────────────────────┬──────────────────────────┐
│ 原视频：播放、慢放、定位   │ 用户目标、场景、困扰       │
│ 时间点与关键帧             │ 本次观察                  │
│ 点击证据跳转到对应时刻     │ 一个主要训练重点           │
│ 替换/补充/移除人工关键帧   │ 一个练习及完成方式         │
│ 自动观察（待确认）         │ 复测条件、检查指标         │
│                          │ 保存草稿 / 预览 / 发布     │
└─────────────────────────┴──────────────────────────┘
```

- 手动保存必须有成功/失败提示；有未保存内容时离开提醒。
- 时间点可由当前播放位置填写；服务端检查位于视频时长内。
- 浏览器 seek 用于定位；精确关键帧由服务端按媒体时间戳解码提取，并返回实际时间戳。不用 `时间 × 标称 FPS` 假装精确帧号，MOV 可变帧率必须覆盖。
- 人工关键帧支持替换、补充和标记不适用，记录原因；不覆盖算法原始输出，不自动重算规则结论。
- 新截图无可靠姿态数据时只显示截图，不伪造角度。
- 算法失败但视频可播放时仍可编辑、发布；媒体不可播放则要求重新上传。

### 4.4 反馈内容契约

| 内容 | 发布要求 |
|---|---|
| `observation` 观察 | 必填，描述本次片段实际可见的现象 |
| `evidence` 证据 | 至少一个时间点或时间段，可关联关键帧 |
| `focus` 本次重点 | 必填，只设一个主要重点 |
| `interpretation` 解释 | 可选，推断须使用不确定性措辞 |
| `drill` 练习 | 必填：动作说明、训练量或完成条件 |
| `retest_instructions` 复测要求 | 必填：场景、拍摄条件、关注内容 |
| `success_criteria` 检查标准 | 必填，允许定性，不要求虚构量化阈值 |
| `author` 反馈者 | 后端记录身份，页面显示真实身份说明 |

示例结构（仅为文案示例，不是对某个真实视频的诊断）：

> 目标：接球后更快出手。观察：片段中接球后有一次额外脚步调整。重点：尝试让接球和脚步准备衔接更连贯。练习：由反馈者填写适合此人的具体练习及训练量。复测：相近位置、传球方式和机位，记录一组投篮。检查：衔接、出手时间与命中表现是否出现变化。

正式发布不能保留“由反馈者填写”等占位内容。没有足够证据时不编造技术建议：标记需要补充视频，填写补拍要求；这不是已交付训练反馈。

### 4.5 用户结果与分享页

顺序：目标 → 本次重点 → 观察与视频证据 → 练习 → 复测要求 → 反馈者 → 折叠的技术细节。

手机单栏，视频全宽，证据可点击定位。内部结果页可查看自动细节；匿名分享响应仅包含明确发布的内容和所需媒体，不返回原始内部结果、存储路径或用户邮箱。

分享由用户主动开启，可撤销。链接绑定一个已发布版本，不会因为管理员修改草稿而变化。重新发布后旧链接仍展示旧版本；用户可以撤销旧链接并为新版本创建新链接。进入复测或修改记录必须登录并通过归属检查。

首版不自动发邮件、私信。用户在站内查看更新；运营人员需要外部通知时自行按用户授权处理。

## 5. 第二阶段：完成复测

### 5.1 流程

1. 用户从已发布反馈点击“Submit a follow-up”。
2. 展示上次训练重点及复测条件，避免凭记忆重新填写。
3. 填写练习记录、选择本次场景并上传新视频。
4. 系统将新视频与这份反馈的具体版本关联。
5. 管理员查看前后对比，为新视频填写并发布下一轮反馈。
6. 历史页按主题展示连续记录；用户可结束主题或再开始新一轮。

只有已发布反馈可作为复测来源。一个来源版本首版只允许一个进行中的复测提交；失败重试复用原提交，完成后可从下一轮反馈继续。

### 5.2 练习记录

| 字段 | 规则 |
|---|---|
| `completion` | 必填：done / partial / not_done |
| `practice_sessions` | 可选，非负整数 |
| `feeling` | 必填：smoother / same / harder / unsure |
| `notes` | 可选，最多 2000 字符，记录困难或未练原因 |
| `attempts`、`makes` | 可选，成对填写；0 ≤ makes ≤ attempts，attempts > 0 |
| `conditions_changed` | 必填布尔值；变化时填写说明 |

未完成练习也允许反馈实际困难，不把它包装为有效的干预效果验证。练习记录先保存为草稿，上传成功后提交；上传失败不丢失文字。

### 5.3 前后对比

- 默认比较“来源反馈对应的视频”与“本次复测”，不固定永远比较首次视频。
- 桌面左右视频，手机上下排列；独立播放、慢放，显示目标和拍摄条件。
- 提供相同语义关键帧的并排展示；缺少某一帧就显示缺失，不用其他帧顶替。
- 第一版不做自动同步播放、不做时间拉伸。点击对应事件分别定位两段视频，时间戳仅属于各自视频。
- 如展示接球到出手用时，两个端点必须有明确事件定义并经人工确认；显示数据来源，无法确认则不展示。
- 命中记录标明“用户自报”及分母；场景变化显著时提示不宜直接比较。
- 新一轮反馈需写明：观察到的变化、继续原重点或更换重点、下一次练习。没有明显改善也是有效结果，不自动制造提升结论。

## 6. 状态与持久化模型

以下均为拟新增结构，正式迁移时核对现有数据库类型。

### 6.1 核心表

| 表 | 主要字段与约束 |
|---|---|
| `training_threads` | id UUID、user_id UUID、goal、problem_description、status(active/closed)、created_at、updated_at |
| `training_submissions` | id UUID、thread_id、analysis_id（唯一）、kind(initial/followup)、shot_context、source_review_version_id（首次为空）、status(draft/submitted/deleted)、idempotency_key、created_at |
| `review_drafts` | submission_id（唯一）、author_subject TEXT、author_display、content JSONB、keyframe_overrides JSONB、revision INT、status(waiting/draft/needs_video/published)、updated_at |
| `review_versions` | id UUID、submission_id、version INT、完整内容与关键帧快照、author_subject、published_at；submission_id + version 唯一，发布后不可变 |
| `practice_logs` | followup_submission_id（唯一）、source_review_version_id、completion、practice_sessions、feeling、notes、attempts、makes、conditions_changed、conditions_note |
| `media_assets` | id UUID、submission_id、kind(original/playback/keyframe)、private_storage_key、mime_type、duration_ms、status(pending/ready/failed/deleting)、created_at |
| `review_shares` | id UUID、review_version_id、token_hash、created_by、revoked_at、created_at |
| `pilot_entitlements` | user_id、enabled、initial_remaining、followup_remaining、updated_at |

JSONB 内容使用独立 Pydantic 模型验证，不能接收任意未校验结构。时间统一存整数毫秒；时间范围满足 0 ≤ start ≤ end ≤ duration。

反馈者标识示例 `local:<id>`、`supabase:<id>`，不得直接外键指向 Supabase UUID。用户归属首版依赖 Supabase 登录；本地管理员只负责审核，不通过内存 fallback 创建正式训练记录。

### 6.2 状态分离

- 媒体状态、自动分析状态、反馈状态分别存储；自动分析失败不等于无法人工反馈。
- 反馈：waiting → draft → published；证据不足时 → needs_video。
- 修改已发布内容只修改草稿，旧版本继续可读；再次发布生成新版本。
- 发布要求媒体 ready、必填内容合格、至少一个有效证据。使用事务写版本并更新当前版本指针；重复发布请求不重复生成版本。
- 草稿 PATCH 带 revision；并发冲突返回 409，禁止静默覆盖另一窗口的修改。
- 复测来源版本必须属于同一用户、同一主题；不得由客户端通过传入其他人的 ID 建立关联。

## 7. 接口设计

均为拟新增接口，业务接口前缀 `/api/v1`。沿用现有自动分析接口，抽取上传公共逻辑，不复制第二套分析算法。

| 方法与路径 | 用途 / 权限 |
|---|---|
| POST `/training-threads` | 创建主题；登录且有试点资格 |
| GET `/training-threads` | 本人主题列表 |
| GET `/training-threads/{id}` | 本人主题、提交及已发布反馈 |
| POST `/training-threads/{id}/submissions` | multipart 上传首次/复测视频及元数据；本人；Idempotency-Key 必填 |
| PATCH `/training-submissions/{id}/practice` | 保存本人未提交的练习草稿 |
| GET `/training-submissions/{id}` | 本人或管理员；分离返回媒体、算法、反馈状态 |
| GET `/admin/reviews` | 管理员待办队列 |
| GET/PATCH `/admin/reviews/{submission_id}` | 获取/保存草稿；PATCH 包含 revision |
| POST `/admin/reviews/{submission_id}/frames` | 按时间提取人工关键帧；管理员 |
| POST `/admin/reviews/{submission_id}/publish` | 校验并发布不可变版本；管理员、幂等 |
| POST `/review-versions/{id}/shares` | 所有者创建分享，返回一次性可复制的完整链接 |
| DELETE `/review-shares/{id}` | 所有者撤销分享 |
| GET `/shared-reviews/{token}` | 匿名读取限定版本 |
| GET `/training-media/{asset_id}` | 所有者/管理员通过鉴权后读取媒体，支持 Range |
| GET `/shared-reviews/{token}/media/{asset_id}` | 每次请求验证链接与媒体归属，支持 Range |
| DELETE `/training-threads/{id}` | 所有者删除主题及关联素材，立即关闭访问 |

提交接口用 JSON 字符串表单项承载练习记录，由模型解析校验。401 未登录；404 资源不存在或不属于访问者；409 状态/版本冲突；422 内容错误；503 持久化不可用。无数据库时新流程不可悄悄降级为进程内存。

配额、提交记录和幂等键以数据库事务/RPC 原子处理。重复上传请求返回已有提交。媒体写入失败可重试且不重复扣资格；后台任务按持久状态恢复，不把 FastAPI BackgroundTasks 当成可靠任务队列。首版允许管理员重试中断任务，重启后不能永久停在 processing。

## 8. 媒体、分享和删除

- 新流程原视频与派生媒体放私有 bucket；本地开发放静态目录外。新接口返回 asset ID，不返回公开对象地址。
- 原始文件保留供解码；如 MOV 编码浏览器不支持，生成可播放 MP4，保留时间映射，正确处理旋转。媒体处理失败显示可重试状态。
- 首版由后端授权代理媒体并支持 HTTP Range。匿名请求每次校验分享 token，不重定向到永久公开 URL；响应使用 private/no-store。撤销后后续请求拒绝访问，已下载内容无法收回。
- 分享 token 使用安全随机值，数据库只存 hash；页面 noindex、Referrer-Policy: no-referrer，日志不得记录完整 token。
- 新流程不会把私有关键帧写入 `/results` 静态目录。公开结果路径相关代码需要为新流程分支调整，不只更改分享页 URL。
- 保留训练主题素材直到用户删除或试点明确结束并另行通知；试点通过人数、上传大小与资格数量限制存储。后续到期策略另定，首版不静默按任务数量删除。
- 删除先撤销分享并禁止新访问，再删除媒体和业务记录；失败进入可重试删除任务。单独删除关联分析不能绕过主题删除规则：旧 DELETE 接口对关联记录返回 409 并提示使用主题管理。
- 旧分析保持原路径行为；原视频已被删的历史任务标记不可播放，需要重新上传，不能承诺恢复。

## 9. 资格与收费边界

沿用普通自动分析的三次免费和现有支付体系。试点资格单独管理，不等同于普通积分。

建议首批每人提供一次首次反馈和一次复测资格，由管理员配置。试点提交通道不扣普通分析积分；资格由后端核验，不能靠客户端 `is_followup` 绕过收费。失败重试复用资格，人工要求补拍也不应再次收费。超出试点次数明确提示联系运营，不在首版新增购买流程。

## 10. 实施顺序与交付物

### 阶段一：能交付反馈

1. 新增数据库迁移、模型、归属校验、试点资格与功能开关。
2. 私有媒体保存与播放；调整成功/失败删除、启动清理和公开输出路径。
3. 上传目标和主题关联；管理员队列与草稿编辑。
4. 人工关键帧定位、内容校验、版本发布。
5. 用户训练卡、分享和撤销；手机端验收。

建议新增 `app/models/training.py`、`app/services/training_service.py`、`app/services/review_service.py`、`app/api/routes/training.py`、`app/api/routes/reviews.py`，以及独立编辑/分享模板和静态脚本。具体数据库 CRUD 可按现有风格接入，避免继续扩大单页脚本。

**完成条件：** 一位试点用户上传真实视频，管理员完成修正并发布一份有具体建议的反馈，用户手机可读、视频可播、链接可撤销；重启服务后仍然可用。

### 阶段二：能完成复测

1. 练习草稿、来源版本关联和幂等复测上传。
2. 前后视频、同语义关键帧比较与场景信息。
3. 新一轮反馈编辑、发布和主题历史时间线。
4. 复测权益及失败恢复验证。

**完成条件：** 同一用户完成一轮练习和复测，管理员能看到来源反馈、练习记录及两段视频，并发布下一轮明确建议。

这两阶段不包含完整运营分析后台。记录必要时间戳和人工处理耗时即可，体验反馈先人工整理。

## 11. 验收与测试清单

| 场景 | 预期 |
|---|---|
| 正常首次上传 → 发布 → 手机打开 | 目标、证据、练习、复测要求完整，媒体可播放 |
| 自动关键帧错误 | 可修正并留下原始结果；用户看到发布版本的修正 |
| 算法失败但视频有效 | 仍可人工交付反馈 |
| 视频损坏或媒体转换失败 | 不允许发布；文字保留，可补拍/重试 |
| 发布后编辑草稿 | 用户、旧分享和复测来源不受未发布修改影响 |
| 两个编辑窗口同时保存 | 旧 revision 返回 409，不覆盖新内容 |
| 无证据或无练习的反馈 | 发布被拒绝，明确指出缺项 |
| 其他用户猜测 ID | 无法读取、修改、关联或播放资源 |
| 撤销分享 | 页面与后续媒体 Range 请求均失效 |
| 第 11 个任务及服务重启 | 训练主题的前次视频与反馈仍存在 |
| 重复提交、网络重试 | 只创建一个提交、只消耗一次资格 |
| 复测记录 makes > attempts | 服务端拒绝 |
| 复测缺少对应关键帧 | 明确显示缺失，仍能独立播放比较 |
| 删除主题时存储暂时失败 | 访问立即关闭，删除可重试 |
| 旧版自动分析与导出 | 原有功能正常；新私有任务不能通过旧导出绕过权限 |

开发时执行相关后端权限、状态、幂等与媒体生命周期测试；前端验证桌面及手机上传/播放/分享/复测。按仓库要求运行 `test_core.py`、`test_import.py`，涉及关键帧逻辑时再跑对应回归。本文档本身未修改算法，不代表这些实现测试已完成。

## 12. 试点判断

初期观察：反馈处理耗时、用户是否理解练习、是否实际完成、是否回来复测、复测后是否愿意继续使用或付费。约五位用户用于发现流程问题，不用于证明市场成立。

若用户看完仍不知道怎么练，优先改反馈内容；若建议理解但无法执行，优先改练习与拍摄要求；若人工无法稳定判断问题，需要先补充专业能力。只有反复验证可靠的判断和建议，才进入后续自动化范围。
